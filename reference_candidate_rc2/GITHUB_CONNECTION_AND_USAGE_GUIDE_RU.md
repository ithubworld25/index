# Подключение GitHub к ChatGPT и рабочий контур визуализаций

## 1. Что GitHub решает в этом проекте

GitHub не является обязательным условием для самой визуализации: автономный HTML и ZIP можно создать локально. В текущем проекте GitHub используется как стабильный производственный контур, потому что временные ссылки среды ChatGPT могут перестать работать после завершения сеанса.

GitHub даёт:

- постоянное хранение исходников и собранных версий;
- отдельные ветки для кандидатов `rc1`, `rc2`, `v1.0`;
- автоматические проверки через GitHub Actions;
- неизменяемые релизные ZIP-файлы с постоянными ссылками;
- историю изменений и возможность сравнить версии;
- безопасное согласование через Pull Request;
- повторяемую пересборку без ручного копирования файлов.

GitHub не заменяет входные документы УП и матриц. В репозитории хранится механизм, тесты и результаты сборки; предметные данные каждой специальности по-прежнему должны быть изолированы.

## 2. Важное различие: чтение и запись

Стандартное подключение GitHub в ChatGPT предназначено прежде всего для чтения, поиска и анализа репозиториев. Возможность создавать ветки, коммиты, Pull Request и релизы зависит от доступного режима ChatGPT, Codex, установленного приложения и политики рабочего пространства.

Параметр `Ask permission` не добавляет новых прав. Он только определяет, когда ChatGPT должен попросить подтверждение перед использованием уже разрешённого действия.

Для производственного контура нужны два уровня доступа:

1. На стороне GitHub — приложению разрешён конкретный репозиторий.
2. На стороне ChatGPT/Codex — доступны действия записи, а режим подтверждения настроен как `Any changes` либо `Always ask`.

## 3. Подключение GitHub

### Шаг 1. Подготовьте репозиторий

Рекомендуемая структура:

```text
organization-or-user/
└── trajectory-visualizations/
```

Для пилота допустим один технический репозиторий. Не используйте основной репозиторий организации, если там есть несвязанный продуктовый код.

### Шаг 2. Подключите приложение в ChatGPT

1. Откройте меню профиля ChatGPT.
2. Перейдите в `Settings` → `Apps`.
3. Найдите `GitHub`.
4. Нажмите `Connect`.
5. В GitHub авторизуйте приложение.
6. Выберите `Only select repositories`.
7. Укажите только технический репозиторий визуализаций.
8. Вернитесь в ChatGPT и дождитесь появления репозитория. Обычно синхронизация занимает несколько минут.

Если репозиторий принадлежит организации, установка приложения может потребовать подтверждения владельца или администратора организации.

### Шаг 3. Настройте подтверждения

В ChatGPT:

1. `Settings` → `Apps`.
2. Откройте подключённый GitHub.
3. В разделе `Ask permission` выберите:

```text
Any changes
```

Это рекомендуемый режим для текущего проекта:

- чтение выполняется без лишних запросов;
- любое изменение во внешнем сервисе требует подтверждения.

Более строгий режим:

```text
Always ask
```

Он требует подтверждения и для чтения. Для повседневной работы обычно избыточен.

Не рекомендуется для пилота:

```text
Never ask
```

В этом режиме изменения могут выполняться без отдельной карточки подтверждения.

### Шаг 4. Проверьте доступ

Проверка чтения:

```text
Покажи ветки и README репозитория owner/repository. Ничего не изменяй.
```

Проверка записи:

```text
Создай в отдельной тестовой ветке файл tmp/connection-test.txt с текстом ok. Основную ветку не меняй.
```

Перед записью должна появиться карточка подтверждения. Проверьте:

- название приложения;
- репозиторий;
- тип операции;
- ветку;
- путь файла.

После проверки тестовую ветку можно удалить.

## 4. Если запись недоступна

Возможные причины:

1. Подключён только стандартный GitHub app с режимом чтения.
2. Работа выполняется не в Codex/Agent-режиме, где доступны действия записи.
3. Администратор ChatGPT Business/Enterprise запретил write actions.
4. GitHub organization не одобрила приложение.
5. Репозиторий не включён в разрешённый список.
6. Защита веток запрещает прямую запись.
7. Используется GitHub Enterprise с IP allowlist без разрешённых адресов OpenAI.

Порядок проверки:

```text
ChatGPT Settings → Apps → GitHub → репозитории и Ask permission
GitHub Settings → Applications → Installed GitHub Apps → Repository access
GitHub Organization Settings → GitHub Apps / Third-party access
Repository Settings → Branches → Branch protection rules
```

Если стандартное приложение даёт только чтение, для записи используйте Codex с GitHub или выполняйте публикацию локально через Git.

## 5. Рекомендуемый рабочий процесс

### Этап 1. Отдельная ветка

Каждая новая версия создаётся в собственной ветке:

```text
trajectory-functional-reference-v0.9-rc2
trajectory-functional-reference-v1.0
specialty-advertising-2026-2027
specialty-oibas-2026-2027
```

Прямые коммиты в `main` не используются.

### Этап 2. Один содержательный пакет изменений

Вместо множества мелких подтверждений объединяйте работу:

1. создать или обновить ветку;
2. записать исходники версии;
3. добавить workflow тестирования;
4. запустить сборку;
5. опубликовать релиз.

Перед каждым внешним изменением просматривайте карточку подтверждения. Не выбирайте `Always allow`, пока процесс не стабилизирован.

### Этап 3. Автоматические проверки

GitHub Actions должен проверять:

- синтаксис inline JavaScript;
- корректность JSON;
- автономность `START.html`;
- отсутствие внешних JS, JSON и `fetch()`;
- светлую и тёмную темы;
- контрастность;
- фильтры компетенций;
- фокус дисциплины;
- проблемы и статусы;
- импорт и экспорт статусов;
- целостность ZIP;
- `START.html` в корне архива.

Сборка не публикуется при падении обязательного теста.

### Этап 4. Pull Request

До фиксации эталона создаётся Draft Pull Request. В нём удобно хранить:

- список изменений;
- результаты тестов;
- замечания РБР и методиста;
- решения по спорным функциям;
- ссылку на кандидатный ZIP.

После принятия команда закрывает замечания и только затем объединяет ветку.

### Этап 5. Release

Для файлов, которые передаются специалистам, используйте GitHub Release asset, а не временный Actions artifact.

```text
Tag: trajectory-functional-reference-v0.9-rc2
Asset: TRAJECTORY_FUNCTIONAL_REFERENCE_v0.9-rc2.zip
```

Actions artifacts имеют срок хранения. Release assets рассчитаны на стабильную выдачу по постоянной ссылке.

## 6. Что проверять в карточке подтверждения

Перед нажатием `Allow once` проверьте:

1. Репозиторий соответствует проекту.
2. Изменяется отдельная рабочая ветка, не `main`.
3. Пути файлов ожидаемы.
4. Нет удаления большого числа файлов.
5. Нет изменения настроек безопасности репозитория.
6. Нет публикации предметных данных другой специальности.
7. Релиз имеет статус prerelease, пока эталон не принят.

Отказывайте в подтверждении, если действие включает:

- удаление веток или релизов без предварительного объяснения;
- запись в основную ветку;
- изменение секретов;
- расширение доступа приложения ко всем репозиториям;
- публикацию исходных конфиденциальных документов.

## 7. Защита репозитория

Рекомендуемые настройки:

- доступ приложения только к одному репозиторию;
- защищённая ветка `main`;
- обязательный Pull Request;
- минимум один review перед merge;
- обязательные status checks;
- запрет force-push в `main`;
- отдельная папка или ветка для каждой специальности;
- отсутствие исходных персональных данных;
- секреты только в GitHub Actions Secrets, никогда в файлах;
- периодическая проверка установленных GitHub Apps.

## 8. Эффективные команды для ChatGPT/Codex

### Анализ без изменений

```text
Проанализируй ветку trajectory-functional-reference-v0.9-rc2. Ничего не изменяй. Выведи только блокирующие дефекты.
```

### Подготовка изменения с подтверждением

```text
Подготовь исправление в отдельной ветке. Перед каждым действием записи запроси подтверждение. Main не изменяй.
```

### Сборка релиза

```text
Запусти workflow сборки. Если тесты прошли, опубликуй prerelease с ZIP и отчётом проверки. Если тесты не прошли, релиз не создавай.
```

### Проверка перед фиксацией

```text
Сравни rc2 с функциональным контрактом. Проверь все обязательные тесты. Не объединяй ветку и не меняй release без отдельного подтверждения.
```

## 9. Когда GitHub можно не использовать

GitHub не требуется, если:

- локальная среда стабильно создаёт ZIP;
- файл можно надёжно зарегистрировать как вложение ChatGPT;
- не нужны версии, командное согласование и автоматические тесты;
- результат одноразовый.

Для текущего проекта GitHub полезен, потому что эталон должен быть воспроизводимым, проверяемым и одинаковым для нескольких чатов и специалистов.

## 10. Отключение доступа

В ChatGPT:

```text
Settings → Apps → GitHub → Disconnect
```

В GitHub:

```text
Settings → Applications → Installed GitHub Apps → ChatGPT/OpenAI → Configure или Uninstall
```

После пилота проверьте список разрешённых репозиториев и удалите временные ветки, тестовые файлы и устаревшие prerelease.
